# services/relay —— 官方中转服务（Phase 2）

**当前状态：未实现。** 这个目录先立在这里，是为了让 Provider 抽象层和目录结构
不用在 Phase 2 重写（见产品策划文档 7.8）。

## 它要解决什么

对国内用户，中转的核心价值不是"多一层代理"，而是解决**跨境访问与支付**两大门槛：
用户不必注册充值三家海外平台，开箱即用，人民币付款。

| | BYOK（未登录/未订阅） | 官方中转（已订阅） |
|---|---|---|
| Key 来源 | 用户自填 | 官方持有，用户无感 |
| 计费 | 用户直接向 Provider 付费 | 扣订阅额度（credit 台账） |
| 使用门槛 | 用户自行注册/充值各平台 | 开箱即用 |
| 责任与限流 | 用户自负 | 官方统一限流与故障处理 |

## 架构（规划）

```
桌面端 ──HTTPS──▶ relay
                  ├─ 鉴权：账号会话 token（短时效 + 设备绑定）
                  ├─ 计量：credit 台账（授予/消耗/退款/调整），幂等键防重复扣费
                  ├─ 限流：账号级并发与速率（Redis）
                  ├─ 缓存：同设定图去重，压低官方成本
                  ├─ 退款：Provider 失败自动返还 credit
                  └─ 转发 ▶ Meshy / Tripo / Rodin / LLM API
```

技术选型：**FastAPI + Postgres（账本）+ Redis（限流/缓存）**，与 sidecar 同栈降低维护成本。

## 部署

中转部署在**海外**（直连各 Provider），面向国内做优化接入线路。
收款：国内微信/支付宝（需经营主体 + ICP 备案），海外 Stripe。
登录双轨：手机号/微信（国内）+ 邮箱/Google（海外）。

## 上线前置条件（硬性）

1. **API 转售合规**：中转本质是转售 Provider 能力，必须逐一确认各 Provider ToS
   或签分销/合作。**未获许可的 Provider 不进中转列表**，用户走 BYOK 直连。
2. **国内 AIGC 合规评估**：订阅上线前完成法务评估（生成式 AI 管理办法 / 备案）。
3. **支付主体**：国内以广州尼特之家信息技术有限公司办理 ICP 备案与商户号；
   海外 Stripe 不支持中国大陆主体，需在"香港/海外关联主体"与
   "Merchant of Record 代收（Paddle / Lemon Squeezy）"之间择一。

以上任一项未完成，中转不开通 —— 客户端只保留路由开关，不保留半成品通路。
